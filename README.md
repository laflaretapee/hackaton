# AI-buddy

Демонстрационная платформа адаптации стажёров для Hack&Change 2026. Независимый хакатонный проект, не официальный сервис Авито. Только синтетические данные и mock-выдача доступов.

Сайт: https://ai-buddy.85.159.231.99.sslip.io
Администрирование: https://ai-buddy.85.159.231.99.sslip.io/admin

## Архитектура

React + TypeScript + Vite → nginx → Go REST API → PostgreSQL 17. Telegram polling и планировщик уведомлений работают в единственном экземпляре backend. Настройки Telegram/RouterAI сохраняются в БД, секреты шифруются серверным ключом. Подробнее: [архитектура](docs/architecture.md), [API](docs/api-contract.md), [OpenAPI 3.1](docs/openapi.json), [исходное ТЗ](docs/master-spec.md).

## Проверка MVP

На странице входа выберите демонстрационную роль и команду Platform. Демо-роли используют только тестовые данные; администратор недоступен через выбор роли. Стажёр проходит план, читает материалы, сдаёт экзамен и создаёт заявку. В отдельном браузере войдите наставником той же команды и согласуйте заявку. Прогресс стажёра и аналитика руководителя обновляются из БД.

[Сценарий показа](docs/demo-script.md), [спецификации](specs/), [статус реализации и фактические проверки](docs/implementation-status.md).

## Настройка администратора

Пароль администратора задаётся `ADMIN_PASSWORD` на сервере и не совпадает с SSH-паролем. Данные доступа передаются владельцу отдельно в локальном файле `.deploy/access.txt` (не включён в Git).

1. Откройте `/admin`, войдите паролем администратора.
2. Telegram: создайте бота через BotFather; укажите токен и username, сохраните, проверьте подключение, включите бота. В BotFather настройте кнопку Mini App на HTTPS-адрес приложения. Единственный экземпляр backend использует polling; при включении интеграции приложение удаляет webhook этого бота. Используйте отдельного бота для проекта. Для реальных согласований сначала зарегистрируйте наставника в той же команде: публичные демонаставники изолированы от Telegram-профилей.
3. RouterAI: получите ключ в личном кабинете российского RouterAI, укажите `https://routerai.ru/api/v1`, выберите модель с поддержкой tools, сохраните и проверьте подключение. Отключите демонстрационный режим после успешной проверки.
4. Пустое поле секрета сохраняет существующий ключ. Для удаления используйте явное действие очистки. Ключи не возвращаются frontend.

Без токенов Telegram и RouterAI сайт позволяет проверить синтетический сценарий. Демо-ответы AI обозначаются явно. Реальный бот, авторизация Telegram, доставка уведомлений и ответы RouterAI требуют действительных ключей и отдельной проверки после их ввода.

Документация провайдера: [RouterAI](https://routerai.ru/docs/guides), [Telegram Mini Apps](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

## Запуск в Docker

Требуются Docker Engine и Compose v2. Создайте `.env` по `.env.example`. Секреты генерируйте криптографически стойким генератором. БД не публикуется в интернет.

```sh
cp .env.example .env
# заполните APP_URL, POSTGRES_PASSWORD, ADMIN_PASSWORD, ENCRYPTION_KEY
# ENCRYPTION_KEY: случайная строка не короче 32 символов (например 64 hex-символа)
docker compose up -d --build
docker compose ps
curl http://127.0.0.1:8095/health
```

Миграции и идемпотентные seed-данные применяются при старте backend. `SECURE_COOKIES=false` допустимо только для локального HTTP. Production должен работать по HTTPS с `SECURE_COOKIES=true`.

## Production

Текущая установка: `/opt/ai-buddy` на предоставленном VPS, собственный compose-проект `ai-buddy`. Host nginx проксирует HTTPS на `127.0.0.1:8095`; остальные приложения сервера используют свои конфигурации.

1. Скопируйте проект на сервер, исключив `node_modules`, `.git` и локальные секреты.
2. Создайте `.env` с правами 0600. Сохраните `ENCRYPTION_KEY` и пароль БД в резервной копии отдельно.
3. Настройте DNS A-запись на IP сервера. Для текущего демо используется публичный sslip.io; для постоянной эксплуатации используйте собственный домен.
4. Выпустите TLS-сертификат через certbot webroot, затем адаптируйте `deploy/nginx.conf` под домен. Выполните `nginx -t` перед reload.
5. Запустите `docker compose up -d --build`, проверьте health, логи и основной сценарий.
6. Для ежедневного backup установите `deploy/ai-buddy-backup.service` и `.timer` в `/etc/systemd/system/`, выполните `systemctl enable --now ai-buddy-backup.timer`.

TLS продлевает certbot; deploy hook должен перезагружать nginx после обновления сертификата.

Для VPS с ограниченной памятью доступна сборка бинарника и SPA на рабочей машине через `scripts/package.sh`, затем `docker compose -f docker-compose.yml -f deploy/compose.prebuilt.yml up -d --build`. Текущая установка использует этот вариант.

## Обновление и резервные копии

```sh
./scripts/backup.sh
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 backend
```

Резервные копии `.deploy/backups/` содержат БД, включая зашифрованные настройки. Без прежнего `ENCRYPTION_KEY` расшифровать их нельзя. Ежедневный backup и пробное восстановление в отдельную БД проверены при развёртывании. Локальные копии сохраняются 14 дней; вынос за пределы VPS настраивается владельцем.

Восстановление (перезаписывает данные выбранной БД, выполняйте осознанно): сначала восстановите SQL в новую пустую БД и проверьте её через `scripts/check-backup.sh`. Для рабочего переключения остановите backend, укажите имя восстановленной БД в `DATABASE_URL` через Compose override и запустите backend. Не загружайте полный дамп поверх существующих таблиц. Удалять volume при обычном обновлении не нужно.

## Проверки

```sh
cd backend
# TEST_DATABASE_URL должен указывать на отдельную тестовую PostgreSQL, не рабочую БД
: "${TEST_DATABASE_URL:?Укажите отдельную тестовую PostgreSQL}"
TEST_DATABASE_URL="$TEST_DATABASE_URL" go test -race -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
cd ../frontend
npm ci
npm run test:coverage
npm run build
cd ..
APP_URL=https://your-domain python3 scripts/smoke.py
```

Для расширенных smoke-проверок передайте `ADMIN_PASSWORD` через окружение; не помещайте его в командную строку или Git. См. отчёт о реально выполненных командах в `docs/implementation-status.md`. Целевое покрытие из ТЗ не считается достигнутым без измерения.

## Ограничения и дальнейшее развитие

Система рассчитана на хакатонный single-instance MVP. Демо-выбор ролей не заменяет корпоративный IAM/SSO. Корпоративные доступы имитируются. Для production нужны корпоративная идентификация, политика хранения, резервные копии вне сервера, нагрузочные испытания и наблюдаемость. План внедрения и метрики представлены в `docs/presentation.md`; бизнес-эффект пока не измерен.
