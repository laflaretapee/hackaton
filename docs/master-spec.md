# 1. Описание продукта

Название: **AI-buddy**

Подзаголовок: **Умная платформа адаптации и обучения стажёров**

Контекст: хакатон Hack&Change 2026, кейс Авито «AI-buddy: ИИ-наставник для стажёров».

## 1.1. Проблема

Новый стажёр приходит в технологическую компанию и сталкивается со следующими трудностями:

- не понимает, какие задачи необходимо выполнить в первую неделю;
- не знает, где находятся корпоративные инструкции;
- постоянно обращается к наставнику с повторяющимися вопросами;
- не всегда понимает, какие материалы изучить перед встречами;
- затрудняется с запросами доступов к репозиториям и инструментам;
- не может самостоятельно оценить собственный прогресс;
- не знает, к кому обращаться по конкретному вопросу.

При этом наставникам приходится тратить время на организационную рутину, а руководителям сложно быстро увидеть общую картину адаптации стажёров.

## 1.2. Предлагаемое решение

Создать единую платформу AI-buddy, объединяющую:

1. Telegram-бота для регистрации, уведомлений и перехода в приложение.
2. Веб-приложение с персональным кабинетом.
3. AI-наставника, понимающего роль, команду и прогресс пользователя.
4. Базу знаний с корпоративными инструкциями и учебными материалами.
5. Индивидуальные программы адаптации.
6. Обучение и mock-экзамены.
7. Выполнение действий через имитации корпоративных API.
8. Мониторинг прогресса для наставников.
9. Аналитику адаптации для руководителей.

**Основная ценность:** уменьшение количества рутинных обращений к наставникам, ускорение адаптации и повышение самостоятельности стажёров.

AI не заменяет наставника. Он автоматизирует повторяющиеся объяснения и организационные действия.

## 1.3. Приоритеты MVP

P0 — обязательно реализовать:

- Telegram-регистрацию;
- авторизацию на сайте;
- роли и разграничение доступа;
- профили и команды;
- индивидуальный чек-лист;
- базу знаний;
- AI-чат с RouterAI;
- ответы со ссылками на источники;
- создание заявки на доступ через mock API;
- сохранение статусов;
- интерфейс наставника;
- функциональные тесты;
- запуск на сервере.

P1 — желательно полностью реализовать:

- mock-экзамены;
- AI-рекомендации по обучению;
- тестовые встречи;
- Telegram-уведомления;
- аналитику руководителя;
- сброс и повторную регистрацию профиля.

P2 — только после завершения P0 и P1:

- расширенную персонализацию обучения;
- графики динамики успеваемости;
- продвинутые AI-рекомендации;
- дополнительные корпоративные сценарии.

Не позволяй P2-функциям задерживать работающий основной сценарий.

# 2. Технологический стек

Используй следующую целевую архитектуру.

## Frontend

- React.
- TypeScript.
- Vite.
- React Router.
- TanStack Query для серверного состояния.
- Zustand для локального состояния.
- Zod для валидации.
- React Hook Form для форм.
- Lucide Icons.
- CSS Modules или аккуратно настроенный Tailwind CSS.
- Адаптивная вёрстка для desktop и mobile.

Выбирай библиотеки осмысленно. Не добавляй зависимости ради количества технологий.

## Backend

Основной язык: **Go**.

Выбери поддерживаемую стабильную версию Go.

Предпочтительная организация:

- REST API;
- модульная архитектура;
- понятные слои handler/service/repository;
- PostgreSQL;
- SQL-миграции;
- строгая типизация входных данных;
- структурированное логирование;
- корректная обработка ошибок;
- контекст и таймауты запросов.

Можно использовать Chi, Gin или стандартный `net/http`, выбрав наиболее удобный вариант.

Не создавай микросервисы без необходимости. Для MVP предпочтителен модульный монолит.

## Database

PostgreSQL — основное хранилище.

Используй миграции, внешние ключи, индексы и ограничения целостности данных.

Для поиска по знаниям сначала реализуй надёжный полнотекстовый поиск PostgreSQL. Если будет доступна подходящая embedding-модель и время на интеграцию, добавь семантический поиск через pgvector.

Не делай проект зависимым от платного embedding API, если можно выполнить основной сценарий без него.

## AI

Провайдер: **RouterAI (https://routerai.ru)**.

Важно: именно российский сервис RouterAI, а не OpenRouter.

Используй OpenAI-совместимый интерфейс RouterAI:

`https://routerai.ru/api/v1`

Конфигурация через переменные окружения:

```env
ROUTERAI_API_KEY=
ROUTERAI_BASE_URL=https://routerai.ru/api/v1
ROUTERAI_MODEL=
AI_REQUEST_TIMEOUT_SECONDS=60
AI_MAX_TOKENS=1500
```

Используй актуальную модель из каталога RouterAI, поддерживающую необходимые возможности. Проверь поддержку tool calling перед окончательным выбором.

Не обращайся к RouterAI из браузера. Все AI-запросы должны проходить через backend.

## Telegram

- Telegram Bot API;
- Telegram Mini Apps;
- webhook в production при наличии HTTPS или long polling с единственным активным экземпляром;
- inline keyboards;
- deep links;
- уведомления через `sendMessage`.

## Deployment

- Docker;
- Docker Compose;
- Nginx или Caddy;
- HTTPS;
- PostgreSQL в контейнере с постоянным volume;
- серверные переменные окружения;
- health checks;
- автоматический перезапуск сервисов.

# 3. Дизайн: интерфейс как у реального продукта Авито

**Это одно из самых важных требований к качеству реализации.**

Не создавай типичный AI-generated dashboard.

Представь, что над продуктом работает профессиональная команда дизайнеров и frontend-разработчиков Авито.

Интерфейс должен выглядеть так, словно это реальный внутренний сервис крупной российской технологической компании.

Изучи открытые материалы о дизайн-системе Авито, официальные продуктовые интерфейсы и их визуальные принципы.

Не копируй закрытые элементы, фирменные материалы, на которые нет прав, и не выдавай демонстрационный проект за официальный продукт Авито.

## 3.1. Визуальный стиль

- Светлый, минималистичный, функциональный дизайн.
- Белые или очень светлые поверхности.
- Читаемая тёмная типографика.
- Сдержанные нейтральные границы.
- Небольшое количество ярких акцентных цветов.
- Разумное использование зелёного, синего и фиолетового цветов.
- Аккуратные радиусы скругления.
- Консистентные отступы.
- Чёткая информационная иерархия.
- Реалистичные таблицы, списки, формы и состояния.

Используй сетку с базовым шагом 4/8 px.

Создай систему дизайн-токенов для цветов, расстояний, радиусов, типографики и теней.

## 3.2. Чего нельзя делать

Не используй:

- огромные градиенты на каждой странице;
- glassmorphism повсюду;
- бессмысленные декоративные карточки;
- чрезмерное количество теней;
- одинаковые большие карточки для абсолютно любой информации;
- огромные пустые пространства ради «воздуха»;
- эмодзи вместо системных иконок;
- случайные цветовые комбинации;
- огромные баннеры «Welcome to AI Future»;
- фальшивые данные без пометки;
- кнопки, которые ничего не делают;
- хаотичные анимации;
- Lorem ipsum.

Не делай интерфейс, который выглядит как шаблон, собранный генератором за несколько минут.

## 3.3. Как проектировать страницы

Для каждой страницы:

1. Определи главную пользовательскую задачу.
2. Выстрой визуальную иерархию.
3. Продумай основной сценарий.
4. Добавь необходимые состояния загрузки.
5. Добавь пустые состояния.
6. Добавь обработку ошибок.
7. Предусмотри мобильную версию.
8. Проверь доступность интерфейса с клавиатуры.
9. Убедись, что основное действие заметно и понятно.
10. Удали элементы, не несущие продуктовой ценности.

Используй нормальные компоненты: sidebar, header, tabs, progress bar, table, dialog, drawer, toast, form fields, breadcrumbs, search.

Пользователь должен понимать интерфейс без инструкции.

## 3.4. Отзывчивость

Поддерживай:

- мобильные экраны от 360 px;
- планшеты;
- desktop;
- Telegram Mini App.

Для desktop используй боковую навигацию там, где это удобно.

Для мобильной версии используй компактную навигацию, адаптивные карточки и удобные touch targets.

Не допускай горизонтального скролла основных страниц.

## 3.5. Требования к качеству

Интерфейс должен выглядеть законченно.

Все значимые кнопки и поля должны иметь реальные состояния.

После действия пользователь должен получать понятную обратную связь.

Для длительных AI-операций показывай состояние ожидания.

Для простых локальных операций ориентируйся на реакцию интерфейса менее одной секунды.

# 4. Пользовательские роли

В системе три роли:

- `intern` — стажёр;
- `mentor` — наставник;
- `manager` — руководитель.

Роль хранится на backend и проверяется при каждом защищённом запросе.

В MVP пользователь может самостоятельно выбрать любую роль для демонстрационных целей.

**Нельзя считать самостоятельный выбор роли полноценной корпоративной авторизацией.** Данные исключительно тестовые.

Предусмотри, чтобы в будущем роли можно было получать из корпоративной IAM-системы.

# 5. Telegram-бот и регистрация

Создай полноценного Telegram-бота.

## 5.1. Начало работы

Пользователь запускает бота командой `/start`.

Бот приветствует пользователя:

«Привет! Я AI-buddy — твой помощник в адаптации. Помогу разобраться в рабочих инструментах, пройти обучение, подготовиться к встречам и отслеживать прогресс».

Затем предлагает выбрать роль.

Кнопки:

- Я стажёр.
- Я наставник.
- Я руководитель.

Используй Telegram inline keyboards.

## 5.2. Выбор направления

После выбора роли пользователь выбирает направление:

- Backend.
- Frontend.
- Продуктовая аналитика.
- QA / Тестирование.
- Data Science.
- DevOps / Infrastructure.
- Product Management.
- UX/UI Design.

Это примерные направления для демонстрационной модели, а не подтверждённая структура команд Авито.

Для каждой специальности должны существовать соответствующие учебные темы и задачи.

## 5.3. Выбор команды

После направления можно выбрать конкретную тестовую команду, например:

Backend:
- Platform;
- Core Services;
- Integrations.

Frontend:
- Web Platform;
- Product Interface.

Analytics:
- Product Analytics;
- Growth Analytics.

Для остальных направлений создай по одной или несколько демокоманд.

Список должен поступать из базы данных, а не быть жёстко связанным с логикой интерфейса.

## 5.4. Создание пользователя

После выбора роли и команды:

- создай пользователя в PostgreSQL;
- сохрани Telegram ID;
- сохрани имя и доступный username;
- назначь роль;
- назначь команду;
- создай программу адаптации;
- создай начальные задачи;
- назначь тестовые учебные материалы;
- установи начальный прогресс;
- создай тестовые события;
- настрой уведомления.

Если роль — стажёр, автоматически назначь наставника из выбранной команды.

Если наставников несколько, используй простую понятную логику распределения.

Если наставника нет, не ломай регистрацию: покажи соответствующий статус.

## 5.5. Завершение регистрации

После успешной регистрации:

«Готово! Твой профиль создан. Теперь ты можешь открыть AI-buddy и начать адаптацию».

Кнопка:

**Открыть AI-buddy**

Кнопка должна открывать реальное веб-приложение.

# 6. Авторизация сайта через Telegram

Нужно создать сайт, который работает:

- внутри Telegram как Mini App;
- в обычном браузере.

## 6.1. Telegram Mini App

При запуске внутри Telegram приложение получает `Telegram.WebApp.initData`.

Frontend передаёт исходные данные на backend.

Backend проверяет Telegram-подпись по официальной документации, срок действия данных авторизации и корректность пользователя.

Никогда не доверяй `initDataUnsafe` без серверной проверки.

После успешной проверки создавай защищённую сессию.

## 6.2. Обычный браузер

Обеспечь вход через официальный Telegram Login или одноразовую ссылку авторизации, подтверждаемую Telegram-ботом.

Не разрешай авторизацию простым указанием Telegram ID.

Используй безопасные cookies (`HttpOnly`, `Secure`, `SameSite` по контексту), защиту от CSRF там, где требуется, и корректное завершение сессий.

## 6.3. Повторная регистрация

Добавь настройки аккаунта:

- смена настроек уведомлений;
- просмотр профиля;
- выход;
- удаление демопрофиля;
- повторная регистрация с другой ролью.

При удалении профиля:

1. Покажи окно подтверждения.
2. Удали или обезличь данные пользователя согласно выбранной политике хранения.
3. Удали его учебный прогресс.
4. Отмени запланированные уведомления.
5. Удали тестовые заявки и связи, если это не нарушает целостность данных.
6. Заверши активные сессии.
7. Верни возможность пройти регистрацию заново.

Продумай безопасную обработку удаления наставника, к которому привязаны стажёры.

# 7. Интерфейс стажёра

Создай полноценный личный кабинет.

## 7.1. Главная страница

На странице должны отображаться:

- приветствие по имени;
- роль и команда;
- текущая неделя адаптации;
- общий прогресс;
- текущие задачи;
- ближайшая встреча;
- следующее рекомендованное занятие;
- недавние результаты обучения;
- активные заявки;
- быстрый доступ к AI.

Пример:

«Привет, Александр! Ты на первой неделе адаптации в Backend Platform. Выполнено 4 из 7 задач. Следующий шаг — изучить Git и пройти короткую проверку знаний».

Прогресс рассчитывай из реальных данных приложения.

Не используй захардкоженные проценты.

## 7.2. План адаптации

Создай страницу с этапами адаптации.

Этапы:

- знакомство с командой;
- рабочие инструменты;
- получение доступов;
- изучение процессов;
- базовое обучение;
- первые задачи;
- подготовка к самостоятельной работе.

Для каждой задачи:

- название;
- описание;
- статус;
- приоритет;
- срок;
- связанные материалы;
- возможность открыть AI-помощника;
- следующий шаг.

Статусы:

- `not_started`;
- `in_progress`;
- `waiting_approval`;
- `completed`;
- `blocked`.

Для каждого статуса используй понятные русские названия.

Не разрешай вручную помечать выполненным действие, которое требует подтверждения от внешнего сервиса, если бизнес-логика этого не предусматривает.

# 8. AI-интеграция через RouterAI

AI — важнейшая функциональная часть продукта.

Не подменяй AI заранее написанными фразами или простым поиском по ключевым словам.

Реализуй настоящий серверный вызов RouterAI.

## 8.1. AI-контекст

При каждом запросе формируй контекст пользователя.

Пример:

```json
{
  "role": "intern",
  "direction": "backend",
  "team": "platform",
  "onboarding_week": 1,
  "completed_tasks": ["team_intro", "git_basics"],
  "current_tasks": ["gitlab_access"],
  "upcoming_lessons": ["code_review"],
  "weak_topics": ["merge_conflicts"]
}
```

Контекст должен формироваться из данных backend.

AI не должен получать персональные данные других пользователей без соответствующих прав.

## 8.2. Поведение AI

AI должен:

- отвечать по базе знаний;
- учитывать текущую роль;
- учитывать команду;
- учитывать этап адаптации;
- предлагать конкретные следующие действия;
- находить нужные инструкции;
- формировать рекомендации;
- объяснять технические темы;
- помогать с подготовкой к экзаменам;
- выполнять разрешённые действия через инструменты.

Если нужной информации нет, AI должен честно сообщить об этом.

Не придумывай корпоративные регламенты Авито.

Тестовые инструкции должны быть явно обозначены как демонстрационные.

## 8.3. RAG и ссылки на знания

Реализуй поиск по базе знаний.

Рекомендуемый конвейер:

1. Получить сообщение.
2. Определить роль пользователя.
3. Проверить права доступа.
4. Найти релевантные документы.
5. Отобрать подходящие фрагменты.
6. Добавить их в контекст LLM.
7. Получить ответ.
8. Вернуть ссылки на точные разделы документов.

Желательно возвращать структурированный результат:

```json
{
  "answer": "Для получения доступа нужно создать заявку.",
  "sources": [
    {
      "document_id": "gitlab-access",
      "section_id": "request-access",
      "title": "Получение доступа к GitLab",
      "url": "/knowledge/gitlab-access#request-access"
    }
  ],
  "suggested_actions": ["create_access_request"]
}
```

Ссылки формируй из реально найденных документов, а не генерируй их произвольно через LLM.

## 8.4. Tool calling

Поддержи вызов инструментов.

Минимальный набор:

```text
search_knowledge_base(query)
get_user_profile()
get_onboarding_progress()
get_upcoming_meetings()
get_learning_recommendations()
get_access_request_status(request_id)
create_access_request(resource_id, reason)
```

При необходимости:

```text
get_available_lessons(topic)
get_exam_results(topic)
suggest_next_lesson()
```

Все инструменты реализуются на backend.

LLM выбирает действие, но не получает прямого доступа к базе данных.

Backend проверяет права, валидирует аргументы и выполняет операцию.

Для изменяющих состояние действий реализуй явное подтверждение пользователя.

## 8.5. AI-память

Сохраняй историю диалогов в PostgreSQL.

Учитывай разумные ограничения длины контекста.

Можно использовать краткое резюме предыдущих сообщений.

Не включай в контекст чужие приватные диалоги.

## 8.6. Отказоустойчивость

Обработай:

- неправильный API-ключ;
- недоступность RouterAI;
- превышение лимитов;
- слишком долгий ответ;
- пустой ответ модели;
- некорректный tool call;
- сбой инструмента;
- недостаток прав.

Добавь таймауты, ограниченные повторные попытки и понятные сообщения об ошибках.

Для демонстрации при отсутствии ключа можно использовать отдельный `AI_MOCK_MODE=true`, однако UI должен явно показывать, что используется деморежим.

# 9. Создание заявок на доступ

Это основной сценарий взаимодействия AI с корпоративным сервисом.

## 9.1. Пользовательский сценарий

Стажёр пишет:

«Мне нужен доступ к backend-репозиторию».

AI:

1. Определяет пользователя.
2. Проверяет роль и команду.
3. Находит инструкцию.
4. Выясняет, к какому ресурсу нужен доступ.
5. Объясняет порядок оформления.
6. Предлагает создать заявку.
7. Получает подтверждение пользователя.
8. Вызывает серверный инструмент.
9. Создаёт заявку через mock API.
10. Показывает номер и статус.

Пример ответа:

«Заявка #REQ-1042 создана. Ресурс: backend-service. Статус: ожидает согласования наставника».

## 9.2. Mock API

Сделай реалистичную имитацию системы заявок.

Функции:

- создание заявки;
- получение заявки;
- просмотр статуса;
- просмотр истории;
- согласование;
- отклонение.

Статусы:

- создана;
- ожидает согласования;
- одобрена;
- отклонена;
- завершена.

Наставник должен иметь возможность согласовать заявку своего стажёра, если этот тип заявки предполагает согласование наставником.

**Важно:** это имитация. Настоящие права к репозиториям и серверам не выдаются.

## 9.3. Связь с прогрессом

Если заявка одобрена и сценарий mock API возвращает успешное выполнение действия:

- обнови статус заявки;
- обнови соответствующую задачу адаптации;
- пересчитай прогресс;
- покажи новый статус стажёру;
- обнови данные дашборда наставника.

Обновление должно происходить через бизнес-логику backend, а не через неподтверждённый текст LLM.

# 14. Тестовые встречи и Telegram-уведомления

Реализуй систему планирования учебных встреч.

Настоящая интеграция с календарём для MVP не требуется.

## 14.1. Создание тестовых событий

При регистрации стажёра создай несколько демонстрационных встреч.

Например:

- Git и Code Review;
- Знакомство с архитектурой;
- Работа с корпоративными инструментами;
- Первая техническая задача.

Встречи должны соответствовать специальности.

Генерируй даты относительно момента регистрации.

Используй разумные рабочие часы и учитывай часовой пояс пользователя.

Случайность допустима для выбора тем и дат, но после создания события должны сохраняться в базе.

## 14.2. Подготовка к встрече

Для встречи должен существовать связанный учебный материал.

За определённое время до встречи, например за 24 часа, отправь уведомление через Telegram.

Пример:

«Привет! Завтра у тебя созвон с наставником по Git и Code Review.

Я подготовил короткое занятие на 10 минут, чтобы ты чувствовал себя увереннее.

Хочешь повторить тему?»

Кнопка:

**Пройти занятие**

Она должна открывать конкретное занятие в веб-приложении.

## 14.3. Планировщик

Реализуй фоновый scheduler или worker.

Планировщик:

1. Ищет события, для которых подошло время уведомления.
2. Проверяет настройки пользователя.
3. Проверяет, не отправлялось ли уведомление.
4. Отправляет сообщение через Telegram Bot API.
5. Сохраняет результат.
6. Обрабатывает ошибки и повторные попытки.

Используй идемпотентность, чтобы одно уведомление не отправлялось многократно.

## 14.4. Настройки

Пользователь может:

- включить уведомления;
- отключить уведомления;
- выбрать период предупреждения;
- посмотреть будущие встречи.

При удалении профиля будущие напоминания должны отменяться.

## 14.5. Демонстрационный режим

Добавь способ создать тестовое событие, которое наступает через 1–2 минуты.

Это необходимо для показа жюри: команда должна иметь возможность продемонстрировать работу Telegram-уведомлений без ожидания следующего дня.

# 17. Разграничение доступа и безопасность

Это обязательная часть архитектуры.

Права:

**Intern**

- видит собственный профиль;
- видит свои задачи;
- проходит обучение;
- использует AI;
- создаёт свои заявки;
- видит свои результаты.

**Mentor**

- видит закреплённых за ним стажёров;
- управляет разрешёнными задачами;
- видит учебный прогресс;
- согласовывает разрешённые заявки;
- не видит чужих стажёров из других областей доступа.

**Manager**

- видит данные команд в своей области ответственности;
- видит сводную аналитику;
- не получает доступ к произвольным приватным AI-диалогам;
- не может выполнять операции от имени стажёра без отдельного разрешения.

Обязательно реализуй:

- server-side RBAC;
- object-level authorization;
- проверку Telegram initData;
- безопасное управление сессиями;
- валидацию входных данных;
- ограничение частоты запросов;
- защиту от prompt injection;
- проверку аргументов AI-инструментов;
- безопасное хранение секретов;
- отсутствие реальных данных сотрудников Авито;
- корректную обработку удаления профилей.

Никогда не доверяй роли, присланной фронтендом, при выполнении защищённой операции.
