# SDD: AI и заявка на доступ

Статус: требуемый сценарий MVP. Точный HTTP-контракт - `docs/api-contract.md`. Настоящие доступы к репозиториям не выдаются.

## Цель и входной контекст

Стажёр просит доступ к ресурсу своей команды. AI находит инструкцию, уточняет ресурс и основание, затем предлагает подтверждаемое действие. Контекст: текущий пользователь, команда, доступные материалы, собственные заявки и задачи. Наличие инструкции не означает разрешение на выдачу доступа.

## Инструменты

- `POST /api/chat {message:string,lesson_id?:string}` возвращает сообщение с возможными `suggested_actions`.
- Серверные операции по смыслу: `search_knowledge_base(query)`, `get_access_request_status(request_id)`, `create_access_request(resource_id,reason)`. Публичная мутация выполняется отдельным подтверждённым запросом.
- `POST /api/requests {resource:string,reason:string,confirmed:true}` возвращает `Request`.
- `GET /api/requests` возвращает доступный текущей роли массив заявок.
- `POST /api/requests/:id/decision {approve:boolean}` разрешён наставнику для назначенного ему стажёра.

## Выходы и изменения состояния

`Request`: `id,resource,reason,status,created_at,user_name,history:[{status,at,note}]`. После подтверждения сохраняются заявка и начальная история. Наставник видит её, принимает решение, mock-интеграция обновляет статус и историю. Только успешное выполнение mock-действия завершает связанную access-задачу и пересчитывает прогресс на backend. Контракт не фиксирует строковый enum `Request.status`; UI использует согласованный с реализацией справочник, не сравнивает русские подписи.

## Ошибки и ограничения

Без `confirmed:true` мутация отклоняется. Пустой/неизвестный ресурс, отсутствие основания, чужая заявка, решение чужого наставника и неподходящее текущее состояние возвращают ошибку `{error:string}`. Повторный клик во время отправки блокируется UI; сервер проверяет переходы состояния. LLM не должен выдавать номер заявки до успешной записи. При отказе mock-сервиса задача не становится выполненной.

## Безопасность

Создатель берётся из сессии, не из тела запроса. Назначение наставника и команда проверяются сервером. Prompt injection в `reason` не влияет на полномочия. Подтверждение привязано к видимым ресурсу и основанию; последующее изменение формы требует нового осознанного подтверждения. Все ресурсы и операции являются демонстрационными.

## Критерии приёмки

1. До подтверждения в списке нет новой заявки.
2. После подтверждения появляется сохранённый ID и история.
3. Только назначенный наставник может согласовать заявку.
4. После разрешённого успешного перехода задача и dashboard показывают согласованный результат после перезагрузки.
5. Отказ или ошибка интеграции не увеличивают прогресс; повторное решение не выполняет действие дважды.

## Проверка

API: intern create → mentor list → decision → intern list/dashboard; отдельно `confirmed:false`, подмена пользователя/ID, чужой наставник, повторное решение и ошибка mock. UI: сверка ресурса в диалоге, spinner, ошибка и повтор. Интеграция с настоящим IAM/Service Desk находится за пределами MVP и требует отдельного адаптера, аудита и проверки идемпотентности.
