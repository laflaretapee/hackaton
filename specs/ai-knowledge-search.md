# SDD: AI-поиск по базе знаний

Статус: спецификация поведения, не подтверждение интеграции. HTTP-схемы определены в `docs/api-contract.md`; ошибки имеют вид `{error:string}`.

## Цель и контекст

Ответить на вопрос стажёра по демонстрационным инструкциям и дать переход к точному разделу. Контекст собирает backend: текущие роль, направление, команда, задачи, результаты обучения и разрешённая история диалога. Неизвестный корпоративный регламент нельзя домысливать.

## Инструменты и входы

- `GET /api/knowledge?q=&direction=` возвращает массив `Article`.
- `GET /api/knowledge/:id` возвращает статью `id,title,category,direction,summary,sections:[{id,title,content}],read,duration_minutes`.
- `POST /api/knowledge/:id/read` возвращает `{ok:true}`.
- `GET /api/chat` возвращает историю `Message[]`; `POST /api/chat {message:string,lesson_id?:string}` возвращает одно новое сообщение.
- Разрешённые серверные инструменты по смыслу: `search_knowledge_base(query)`, `get_user_profile()`, `get_onboarding_progress()`, `get_upcoming_meetings()`, `get_learning_recommendations()`. Имена инструментов провайдера внутренние и не создают отдельные публичные HTTP-маршруты.

## Выходы и алгоритм

Backend проверяет сессию, находит релевантные статьи PostgreSQL, выбирает фрагменты и передаёт ограниченный контекст RouterAI через OpenAI-совместимый API `https://routerai.ru/api/v1`. Ответ `Message` содержит `id,role,content,sources?:[{title,url}],suggested_actions?:string[],created_at`. Ссылки строятся из реальных ID статьи/раздела, например `/knowledge/<article-id>#<section-id>`, а не из выдуманного текста LLM. История сохраняется в PostgreSQL.

При недостатке источников ответ прямо сообщает об ограничении и предлагает уточнить вопрос. Деморежим AI отдельно обозначается: он позволяет проверить интерфейс и поиск, но не доказывает вызов LLM.

## Ошибки и ограничения

Пустой/слишком длинный вопрос, неизвестное занятие, неподходящий ответ модели, некорректные tool-аргументы, таймаут, лимит провайдера и неверный ключ обрабатываются без фиктивного успешного ответа. UI завершает состояние ожидания и позволяет повторить запрос. Число внутренних шагов и размер истории ограничиваются. Семантический поиск/pgvector не являются обязательной частью MVP.

## Безопасность

Ключ RouterAI остаётся на backend. Контент статьи и пользователя не может менять системные правила, расширять права или создавать заявку. LLM не получает SQL и произвольный сетевой доступ; tool calls выполняются по allowlist с проверкой аргументов. Чужие диалоги не попадают в контекст. HTML/Markdown и ссылки отображаются безопасно; текст AI не считается доказательством завершения задачи.

## Критерии приёмки

1. Вопрос по Git возвращает связанное объяснение и открываемый существующий раздел.
2. Неизвестный регламент не сопровождается придуманным источником.
3. История видна после перезагрузки только своему пользователю.
4. Ошибка провайдера не оставляет вечный spinner и не раскрывает ключ.
5. Публичный `GET /api/public/config` честно сообщает `ai_mock_mode`.

## Проверка

Unit/API: поиск с опечатками/пустым результатом, допустимые tool calls, невалидные аргументы, таймаут/пустой ответ, изоляция истории. E2E: вопрос → источник → статья → повторный вход. Отдельный live-тест RouterAI выполняется только после настройки ключа и модели; результат не подменяется mock-проверкой. Метрики качества ответов требуют размеченного набора вопросов и пока не измерены.
