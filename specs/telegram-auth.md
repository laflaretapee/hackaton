# SDD: Telegram и сессии

Статус: спецификация поведения MVP, не отчёт о выполненных проверках. Источник HTTP-схем: `docs/api-contract.md`. Общие правила: JSON, строковые ID, ISO8601, ошибки `{error:string}`; списки возвращаются массивами.

## Цель и контекст

Связать Telegram-пользователя с демонстрационным профилем и открыть кабинет без передачи Telegram ID как доказательства личности. Бот собирает роль, направление и команду. Самостоятельный выбор роли допустим только для синтетических демоданных; он не заменяет IAM.

## Инструменты и входы

- `GET /api/teams` возвращает `[{id,name,direction}]` для выбора команды.
- `POST /api/auth/telegram {init_data:string}` принимает исходный `Telegram.WebApp.initData`.
- `GET /api/auth/login-link` возвращает `{url:string,token:string}` для входа через обычный браузер. Бот подтверждает одноразовый токен; `POST /api/auth/exchange {token:string}` завершает вход. Пока подтверждения нет, контракт предусматривает HTTP 409.
- `POST /api/auth/demo {role:"intern"|"mentor"|"manager",name?:string,team_id?:string}` доступен в разрешённом деморежиме. Демонаставник - общий seeded-профиль для демостажёров.
- `GET /api/me` возвращает текущего пользователя; `POST /api/auth/logout` и `DELETE /api/me` возвращают `{ok:true}`.

## Ожидаемые выходы

Успешный вход устанавливает серверную сессию и возвращает `User`: `id,name,role,team_id,team_name,direction,mentor_name,notifications,reminder_minutes,telegram_id?,is_demo`. После выхода прежняя сессия больше не открывает защищённые данные. Удаление демопрофиля завершает сессии, отменяет будущие уведомления и убирает персональный прогресс с сохранением целостности связей.

## Ошибки и ограничения

Некорректная/просроченная подпись, отсутствующий профиль, неподтверждённый или повторно использованный токен не дают сессию. При ненастроенном боте UI объясняет необходимость настройки; демовход не выдаётся за Telegram-вход. Ошибки возвращаются структурированно без токенов и секретов. Конкретные HTTP-коды, кроме 409 для pending exchange, уточняются реализацией.

## Безопасность

Backend проверяет подпись и возраст `initData`; `initDataUnsafe` не является источником доверия. Браузерные токены одноразовые и ограничены сроком жизни. Cookies: HttpOnly, Secure в HTTPS, SameSite; мутации проверяют origin. Роль администратора отсутствует в публичной регистрации. Telegram-токен хранится на сервере в зашифрованных настройках и никогда не передаётся клиенту.

## Критерии приёмки

1. Оба Telegram-пути открывают один и тот же сохранённый профиль.
2. Повтор обмена одноразового токена отклоняется; pending exchange не создаёт сессию.
3. Поддельная подпись и устаревшие данные отклоняются.
4. Logout и удаление профиля действительно закрывают доступ с прежней cookie.
5. Демо-роль и ограничения данных видны пользователю.

## Проверка

Unit: валидная/изменённая подпись, границы возраста, одноразовость. API: вход → `/api/me` → logout → отказ, удаление и повторная регистрация. E2E с настоящим ботом требует токена, HTTPS и настроенного Mini App; пока токены не предоставлены, этот пункт остаётся внешней проверкой. Зафиксировать фактические результаты в `docs/implementation-status.md` после запуска.
